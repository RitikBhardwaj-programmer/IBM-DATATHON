01

The existing landscape

Federated learning tooling is a genuinely mature space — several frameworks have been in production use for years. None of them will hand you a finished demo, but all of them remove the hardest infrastructure problem: coordinating training across clients that never share raw data.

Recommended base

Flower (flwr)

Framework-agnostic (PyTorch, TensorFlow, scikit-learn, plain NumPy), actively released on a roughly monthly cadence through early 2026, strong docs, and a built-in simulation mode that runs many "clients" on one laptop — exactly what a 24-hour team needs. Ships official examples for both differential privacy (via Opacus) and secure aggregation (SecAgg+) that you can adapt directly.

Strong narrative, riskier build

IBM federated-learning-lib (IBM FL)

IBM's own open-source enterprise FL framework — supports FedAvg, FedProx, Krum, and Byzantine-tolerant aggregators, plus built-in differential privacy and even fully homomorphic encryption. The obvious platform-story fit for an IBM-judged event, but its last tagged release was August 2023, so expect thinner community support if you hit a bug mid-event.

Healthcare-grade, heavier setup

NVIDIA FLARE

Battle-tested in real hospital deployments, strong security/governance model. Smaller community and more enterprise-oriented setup than you need for a 24-hour build.

Medical-specific, Kubernetes-heavy

Substra

Purpose-built for cross-institution medical data by Owkin, now under the Linux Foundation. Requires a Kubernetes node per participant — too much infrastructure overhead for a single sprint.

Research-oriented

PySyft (OpenMined)

Strong on encrypted computation research, but needs its companion PyGrid layer for real network deployment — more moving parts than Flower for the same demo.

Finance-grade, steep curve

FATE (WeBank)

Serious industrial FL used in banking; requires protocol-buffer definitions for custom models. Powerful, but the learning curve doesn't fit a 24-hour window.

Bottom line: build on Flower. It's the only option here where "install it, run the quickstart, adapt the DP and secure-aggregation examples" is realistically a same-day path. Mention IBM FL in your pitch as evidence IBM itself has invested in this exact problem — you don't need to run your demo on it to make that point.
02

What to actually improve

Because the core coordination problem is already solved by Flower, "build federated learning" by itself won't read as novel to a judge who's seen a Flower quickstart before. The improvement is a stack of four things layered on top of the baseline — each one answers a real, named weakness of plain FedAvg.

01

Formal privacy guarantee — DP-SGD via Opacus

Plain federated learning still leaks information through model updates. Wrapping local training with Opacus's PrivacyEngine clips per-sample gradients and adds calibrated noise, giving you an actual (ε, δ) number to put on a slide — "we can state exactly how much privacy each hospital is guaranteed," not just "we don't move the data."

Answers: FedAvg alone has no formal privacy proof.
02

Secure aggregation — Flower's native SecAgg+

Even with DP, a plain FL server still sees each client's individual update before averaging. SecAgg+ uses cryptographic masking so the server only ever sees the sum of updates — no single hospital's contribution is ever visible on its own. Flower ships a working example of this protocol you can adapt rather than implement from scratch.

Answers: the server itself is a trust bottleneck in vanilla FedAvg.
03

Faster convergence on realistic (non-IID) data — swap the strategy

Real hospitals or banks don't have identically distributed data — one may see mostly older patients, another mostly a different fraud pattern. Plain FedAvg converges slowly or unevenly here. Swapping in Flower's built-in FedProx or an adaptive server optimizer like FedYogi/FedAdam is a one-line strategy change that measurably cuts the number of rounds needed — a concrete "more efficient" number for your pitch.

Answers: FedAvg assumes data is more similar across clients than it really is.
04

A live dashboard — the gap none of these frameworks fill

Every framework above is CLI- or notebook-first; none ship a judge-friendly way to see what's happening. A small Streamlit or Flask page that plots accuracy per round, privacy budget (ε) spent so far, and bytes transferred turns an invisible background process into something a judge watches happen live — this alone is a genuine, demoable point of originality.

Answers: "trust me, it's private and it's converging" is not a demo.

If you only have time for two of the four

Do the DP-SGD layer and the dashboard first. The DP guarantee is what makes the "without exposure" half of the theme name literally true and gives you a hard number to defend under questioning; the dashboard is what makes the judges actually watch it happen instead of taking your word for it. SecAgg+ and the strategy swap are genuine technical upgrades but are lower priority if the clock runs out — say so honestly in your pitch as "documented next step" rather than skipping the mention entirely.

03

Concepts you need to actually understand

Not just tool names — the ideas behind them, because judges will ask "why does this work" and "you used sklearn" isn't an answer.

ML foundations

  • Training loop basicsforward pass, loss, backward pass, optimizer step
  • Train/validation/test splitand why leakage between them invalidates your accuracy number
  • Overfitting vs. generalizationespecially relevant since each client sees less data than a centralized model would
  • Evaluation metricsaccuracy alone is misleading on imbalanced data (fraud, rare disease) — learn precision, recall, F1, and why they matter here

Federated learning core

  • Client–server FL architecturelocal training rounds vs. global aggregation rounds
  • FedAvgweighted averaging of client model updates by local dataset size
  • The non-IID problemwhy data being different across clients breaks naive averaging
  • FedProx / FedYogi / FedAdamwhat each changes about the baseline and why it helps
  • Partial participationhandling clients that drop out or sample only a subset each round

Privacy & security

  • Differential privacy intuitionadding calibrated noise so no single record's presence is provable from the output
  • ε (epsilon) and δ (delta)what a "privacy budget" actually means, and that smaller ε = more privacy but less accuracy
  • DP-SGDper-sample gradient clipping plus noise injection, and why it needs different sampling (Poisson, not sequential)
  • Secure aggregationthe idea of cryptographic masking so a server sees only a sum, never an individual update
  • (Stretch) Homomorphic encryptioncomputing directly on encrypted values — mention as a future direction even if you don't implement it

Efficiency

  • Communication costwhy bytes transferred per round matters as much as accuracy in a real deployment
  • Quantization / sparsificationsending compressed or partial updates instead of full-precision full models
  • Convergence speedrounds-to-target-accuracy as a metric distinct from final accuracy

How the pieces fit together

A simplified view of one training round in your demo — this is what you're actually walking judges through.

Client AHospital / bank shard, local data never leaves
→
Local DP-SGDOpacus clips + adds noise
→
Masked updateSecAgg+ hides it from the server
→
Flower serverFedProx/FedYogi aggregation
→
Live dashboardaccuracy · ε spent · bytes sent

The updated global model then loops back down to every client for the next round. Clients B and C (your other simulated hospitals/banks) run the same left-hand path in parallel — Flower's simulation mode lets you run all of them as processes on one machine for the demo, no separate physical devices required.

06

Suggested learning order

Mapped onto the same four-week window from the main playbook — this slots into "Week 2: de-risk the platform" and "Week 3: build the MVP."

Days 1–2

PyTorch refresher + Flower quickstart

Run Flower's official quickstart in simulation mode with a toy dataset (e.g. partitioned MNIST) so the client/server/strategy structure is muscle memory before you touch your real data.

Days 3–4

Swap in your real (non-IID) dataset

Pick a small tabular or image health/finance dataset (a MedMNIST subset like PneumoniaMNIST, or Kaggle's Credit Card Fraud dataset), partition it deliberately unevenly across 3–5 simulated clients, and get a plain FedAvg baseline training end to end.

Days 5–6

Layer in Opacus

Adapt Flower's official Opacus example to your model. Expect an accuracy drop — this is normal and is itself part of your story (state the privacy/accuracy tradeoff honestly with real numbers).

Days 7–8

Add SecAgg+ and try FedProx/FedYogi

Adapt Flower's secure-aggregation example; swap your strategy from FedAvg to FedProx or FedYogi and compare rounds-to-target-accuracy against the baseline.

Days 9–10

Build the dashboard

Stand up the Streamlit/Flask view plotting accuracy, ε spent, and bytes transferred per round, reading from the same logs your Flower run already produces.

Ongoing

Train your centralized baseline

Keep a scikit-learn (or simple PyTorch) centralized model trained on the pooled data running alongside — your comparison number against the federated result is one of the most persuasive things you can show a judge.

Framework maturity and version details reflect Flower's public release history through early 2026 and the current state of the other frameworks' public repositories — re-check exact version numbers before the event, since these projects release frequently.
