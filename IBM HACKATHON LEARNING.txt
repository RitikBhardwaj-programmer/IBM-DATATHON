# 4. Federated Learning — core idea

We established:

### Traditional centralized ML

```text
Hospital A ─┐
Hospital B ─┼──→ Central Server
Hospital C ─┘
             ↑
       raw patient data
```

The problem:

> Sensitive data has to leave the organizations.

### Federated Learning

```text
             Global Model
                  ↓
       ┌──────────┼──────────┐
       ↓          ↓          ↓
   Hospital A Hospital B Hospital C
       ↓          ↓          ↓
   Local data  Local data  Local data
       ↓          ↓          ↓
     Update     Update     Update
       └──────────┼──────────┘
                  ↓
              Aggregate
                  ↓
            Global Model
```

The raw training data stays at each client.

So:

> **FL answers: "Where does training happen?"**

Answer: **at the data owner/client.**

# 6. Model

A model is essentially a mathematical function with **learnable parameters**.

We used:

```text
y = wx + b
```

as the simplest intuition.

- `w` = a learnable parameter
- `b` = another learnable parameter

Training means:

> Adjust the parameters so predictions become better.

# 7. Forward pass

```text
Input
  ↓
Model
  ↓
Prediction
```

Example:

```text
patient information
       ↓

       ↓

```

# 8. Loss

Loss measures:

> **How wrong was the prediction?**

Large loss → prediction is poor.

Small loss → prediction is closer to the desired answer.

---

# 9. Backward pass

The backward pass calculates **gradients**.

The gradient tells us approximately:

> "If I change this parameter, which direction should I move it to reduce the loss?"

---

# 10. Optimizer

The optimizer uses the gradients to update model parameters.

Conceptually:

```text
Prediction
    ↓
Loss
    ↓
Backward pass
    ↓
Gradients
    ↓
Optimizer
    ↓
Updated parameters
```

# 13. Classification metrics

We covered:

### Accuracy

```text
correct predictions
-------------------
all predictions
```

But accuracy can be misleading with imbalanced datasets.

### Precision

> Of the things the model predicted as positive, how many were actually positive?

### Recall

> Of all actual positives, how many did the model find?

### F1

Balances precision and recall.

# 14. Differential Privacy

This was one of the major sections we completed.

The intuition:

> A person's presence or absence in the dataset should not dramatically change what an observer can learn from the released result.

We discussed the formal idea that output distributions should be difficult to distinguish when one person's record is added or removed.

---

# 15. Epsilon and delta

Differential Privacy uses:

- **ε (epsilon)**
- **δ (delta)**

The important intuition we established:

> Generally, smaller ε means a stronger privacy guarantee, often at the cost of more noise / reduced utility.

We specifically avoided treating DP as "make inference impossible."

DP provides a **formal bound on individual influence**, not magical invisibility.

---

# 16. Gradient clipping

Important correction we established:

Gradient clipping means:

> Limit the **norm/magnitude of each per-example gradient**.

Not simply:

> "Every individual gradient value must be below some maximum."

---

# 17. DP-SGD

We learned the correct sequence:

```text
Training examples
       ↓
Per-example gradients
       ↓
Clip each gradient
       ↓
Aggregate
       ↓
Add calibrated noise
       ↓
Optimizer
       ↓
Update parameters
```

Very important:

> Noise is added to the gradient/aggregated gradient **before the optimizer updates the model parameters**.

> **Federated Learning alone does NOT guarantee privacy.**

# 20. Secure Aggregation

Another major section already completed.

The problem:

Even if raw data never leaves the hospital, the server might receive:

```text
Hospital A → update A
Hospital B → update B
Hospital C → update C
```

The server could potentially inspect individual updates.

Secure Aggregation addresses this.

---

# 21. Secure Aggregation intuition

Suppose:

```text
A = 120
B = 80
C = 200
```

They add masks:

```text
A → 120 + 37
B →  80 - 91
C → 200 + 54
```

The masks sum to zero:

```text
+37 -91 +54 = 0
```

Therefore:

```text
masked sum = actual sum
```

but the server doesn't directly see each client's original value.

Actual aggregate:

```text
120 + 80 + 200 = 400
```

The server gets the aggregate without learning each individual contribution in the intended protocol model.

---

# 22. Secure Aggregation vs DP

We established that they address different threats:

```text
Federated Learning
→ keeps raw data local

Differential Privacy
→ limits individual influence

Secure Aggregation
→ hides individual client updates from the aggregator
```

Together:

```text
                 Federated Learning
                        │
              raw data stays local
                        │
                ┌───────┴───────┐
                ↓               ↓
              DP              SecAgg
         limit influence    hide updates
```

# 26. FedAvg

FedAvg = **Federated Averaging**

Basic idea:

```text
Global Model
     ↓
 ┌───┼───┐
 ↓   ↓   ↓
 A   B   C
 ↓   ↓   ↓
updates
 └───┼───┘
     ↓
 weighted average
     ↓
New Global Model
```

The weighting is generally based on the amount of local training data.

We solved examples such as:

### Equal data

A:

```text
[0.6, 0.4]
```

B:

```text
[0.8, 0.2]
```

Average:

```text
[0.7, 0.3]
```

### Unequal data

If A has 100 examples and B has 900:

```text
A weight = 0.1
B weight = 0.9
```

So B's update has much more influence.

---

# 27. Important distinction: parameters vs updates

We discussed this carefully.

### Parameters

The actual current model values.

### Update

Conceptually:

> How the client changed/contributed relative to the global model.

Depending on the implementation, the communication may involve full parameters or deltas.

So don't assume that the network protocol must literally transmit "gradient vectors."

# 29. Local epochs vs FL rounds

### Epoch

### FL round

```text

```

cycle.

These are **not the same thing**.

# 31. FedProx

We already covered FedProx.

The intuition:

> **FedProx tries to prevent excessive local drift from the global model.**

Rubber-band analogy:

```text
             Global Model
                  ●
                 / \
                /   \
               /     \
              ●       ●
             A         B
```

The local models can move toward their local-data optimum, but the proximal term discourages moving too far from the global model.

We explicitly established:

> FedProx is **not automatically superior** to FedAvg.

The correct experimental statement would be something like:

> "In our experiment, FedProx reached the target F1 in fewer rounds."

Not:

> "FedProx is always better."

---

# 32. FedAdam and FedYogi

We also covered adaptive server-side optimization.

High-level distinction:

| Method | Main idea |
|---|---|
| **FedAvg** | Average client updates |
| **FedProx** | Reduce excessive local drift |
| **FedAdam** | Adaptive server-side optimization |
| **FedYogi** | Adaptive server-side optimization |

Important distinction:

> **FedProx changes the local objective.**

> **FedAdam/FedYogi primarily change how the server updates the global model.**

For experiments, useful practical measurements include:

# 35. Quantization

Quantization means using fewer bits / lower precision to reduce the size of communicated information.

Intuition:

```text
32-bit representation
        ↓
8-bit representation
        ↓
smaller communication payload
```

Trade-off:

> Smaller communication cost can come at the cost of approximation/error.

# 37. PyTorch training loop

You learned this structure:

```python
for x, y in dataloader:
    optimizer.zero_grad()
    prediction = model(x)
    loss = loss_function(prediction, y)
    loss.backward()
    optimizer.step()
```

And what each step means:

```text
zero_grad()
    ↓
clear old gradients

model(x)
    ↓
forward pass

loss(...)
    ↓
measure error

loss.backward()
    ↓
calculate gradients

optimizer.step()
    ↓
update parameters
```
